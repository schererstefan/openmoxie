### B. Full Control API

- `site/hive/mqtt/control_commands.py` (new, 213 lines) — single pure shaping/validation module, no publishing:
  - `phonetic_name()`: `\bMycroft\b` case-insensitive → `"my croft"`; `"my craft"` left alone; substrings (`Mycroftian`) untouched; non-strings returned as-is.
  - Gesture allowlist `GESTURE_BEHAVIOURS`: loaded at import from `doc/AssetBundleMasterManifest.csv` (path resolved from `__file__`, works in clone and in the `COPY . /app` image) as `BehaviourTree` rows with `Default=True` (574 labels at base commit; a test re-reads the CSV independently and asserts equality). Missing manifest fails closed (empty set → every gesture rejected). Look allowlist is exactly the five specified trees, default `bht_sensoryidlefacetracker_anim`.
  - Dance: `ALLOW_DANCE_MODULE = False` module constant (simpler/reviewable choice — enabling dance is a deliberate code edit here, no DB/UI toggle), `DANCE_MODULE_ID = "DANCE"` fixed, `build_dance_payload()` rejects any other `module_id` and refuses while the flag is off. `build_sleep_payload()` / dance payload are `Volley.add_response_action`-shaped `remote_chat` dicts.
  - `behaviour_tree_mark()` emits exactly one `cmd:behaviour-tree` mark in the `doc/Markup.md` "Changing Behavior Trees" format (`behaviour` field = the allowlisted Lbl, `action:0`), with `duration` validated numeric and clamped to 0.1–30.0 s. Validators: `validate_intensity` (0.0–1.0), `validate_mood` (the 12 puppet-page moods), `parse_duration`, `parse_single_command` + `validate_single_movement` (see bundling rule below).
- `site/hive/mqtt/moxie_server.py`: new `send_telehealth_behaviour(device_id, behaviour, speech="", duration=1.0)` publishing the same telehealth shape as speech (`PLAY_OUTPUT`, `output.text` = spoken text or `""`, `output.markup` = single behaviour mark, with spoken text appended after the mark for speak+gesture). Callers must allowlist first; the mark builder re-checks.
- `site/hive/views.py` (`puppet_api`): GET keeps `online`, `puppet_state`, `puppet_enabled` and adds `dance_enabled` (flag state) + `control_commands` (the 9-command list); GET publishes nothing. POST keeps `enable`/`disable` (config + save + `handle_config_updated`), `interrupt`, and `speak` returning the existing `{'result': True}`; `speak` now phonetic-renders the name at the API boundary and validates mood/intensity (see §B.6). New POST commands return `{'result': …, 'command': …}`: `gesture` (requires allowlisted `behaviour`; optional `speech` → speak+gesture, optional `duration`), `look` (optional `behaviour`, default face-tracker; gesture-valid-but-not-look trees rejected), `dance` (remote_chat launch `DANCE`, flag-gated), `sleep` (remote_chat sleep action), `wake` (`send_wakeup_to_bot`, returns its bool; offline ⇒ HTTP 200 with `result: False` and no publish). Transports are existing `MoxieServer` methods only (`send_telehealth_behaviour`, `send_command_to_bot_json`, `send_wakeup_to_bot`).
  - Bundling rule (one command per POST): a `commands` field, or a `command` value with more than one token (`gesture,dance`, `gesture+dance`, `gesture dance`), or a missing/empty `command` ⇒ 400 and nothing is published. Because exactly one command is accepted, at most one movement command (`gesture|dance|look|sleep`) can ever be issued per call; nothing is queued.
  - Validation ⇒ 400 `{'result': False, 'error': …}` (unknown device keeps the pre-existing bare `HttpResponseBadRequest`): unknown command, non-allowlisted behaviour, dance with `module_id != DANCE` or flag off, intensity outside 0.0–1.0, unknown mood, missing `speech`, non-numeric `duration`. Command names are the exact lower-case strings; there is no `pose` alias.

## B.6 Deviations and deliberate interpretations (with reasons)

- **Resolution consequence (confirm wanted):** implementing Stage 1 §B.1 exactly means stock conversations (`vendor = OPEN_AI`) with an OpenAI key configured stay on GPT even when the global `chat_provider` is set to Muse Spark; the global decides only when the vendor provider has no key (or for sessions with no vendor). Switching a conversation therefore also requires its Admin `vendor` (+`model`) change. This matches the spec text ("vendor if its key is configured") and keeps GPT bit-stable, but if Stefan expected the setup switch alone to move all chat, say so and the one-function change is in `ai_factory.resolve_chat_provider`.
- Two thin `create_chat_client` dispatchers (factory-canonical + conversations-local through module-level factory names). Reason: `test_chat_models.py` patches `hive.mqtt.conversations.create_openai`; dispatching conversations through `ai_factory.create_chat_client` would break that unmodified suite. Both dispatchers are covered by tests asserting identical routing.
- `create_openai()` now passes `timeout=20.0` (was: SDK default). Reason: Stage 1 §B.2/Stage B require ~20 s on chat clients and say "both constructors". Side effect to be aware of: Whisper STT requests, which share `create_openai()`, also get a 20 s timeout. If long transcriptions ever need more, give STT its own constructor timeout in a later change — routing/provider isolation is unaffected.
- Fail-loudly pre-check is explicit for the Spark branch only. OpenAI-with-no-key keeps today's behaviour exactly (SDK construction raises → `WARNING` → existing fallback speech), preserving the GPT-default fence; the existing test asserting that fallback passes unmodified.
- `speak` hardening (was: raw `request.POST[...]`/`float(...)` → 500 on bad input, any mood string passed through; unknown commands silently returned success): now missing speech / unknown mood / intensity outside 0.0–1.0 / unknown command ⇒ 400, per Stage A §A.3/§A.5 validation. The puppet page already sends only valid values, so the UI path is unchanged; malformed programmatic callers now get a 400 instead of a 500/silent success.
- Dance flag is a code constant (`ALLOW_DANCE_MODULE = False`), not a DB/UI setting — the simpler, diff-reviewable option allowed by the Stage B brief. `dance_enabled` in GET status reflects it.
- Behaviour mark uses the `doc/Markup.md` tree-changing form (`behaviour` = Lbl, `action:0`) rather than the automarkup engine's in-speech gesture form (`eventName` = Lbl, `action:4`). Stage A §A.1 points at the documented form; which one the robot honours for standalone telehealth output is live-unproven either way and is the first thing to check in a live gesture test.
- `HiveConfiguration.muse_spark_model` field was added beyond the two named model fields so the required setup-page model selector persists; per-conversation `SinglePromptChat.model` still wins for its conversation (the selector writes only the global suggestion, per Stage 1 §B.6).
- Not done, deliberately: stale "3.5 turbo" setup copy, `doc/ChatModels.md`/README updates, and the optional opt-in "fall back to GPT" toggle (Stage 1 §B.5 — only if Stefan asks). No other files outside this clone were created except throwaway verification scripts in `/tmp` (`stageb_verify.py`, `stageb_migration_check.py`), kept there for re-running.
