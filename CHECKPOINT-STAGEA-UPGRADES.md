## A.1 What exists today (code-verified)

### Puppet API — the only existing server-side control surface
- `site/hive/views.py`, `puppet_api(request, pk)` (approx. lines 243-279 in the base file; function `MoxiePuppetView` + `puppet_api`):
  - GET returns `{online, puppet_state, puppet_enabled}` where `puppet_enabled` is `device.robot_config["moxie_mode"] == "TELEHEALTH"`.
  - POST commands, all `@csrf_exempt`, all returning `{'result': True}` on success: `enable` (sets `moxie_mode=TELEHEALTH`, saves device, `handle_config_updated`), `disable` (pops `moxie_mode`), `interrupt` (`send_telehealth_interrupt`), `speak` (`send_telehealth_speech(device_id, speech, mood, float(intensity))`).
  - No gesture, dance, look, wake, or sleep command exists in this API. Any new control command must be added here, reusing its POST shape and its `MoxieDevice.DoesNotExist -> HttpResponseBadRequest` path.
- `site/hive/mqtt/moxie_server.py`:
  - `send_command_to_bot_json(device_id, command, payload)` publishes JSON to `/devices/{device_id}/commands/{command}`.
  - `send_telehealth(device_id, msg)` publishes `{"command": "telehealth", "message": msg}` on the `telehealth` command topic.
  - `send_telehealth_speech(device_id, speech, mood, intensity)` builds markup via `RemoteChat.make_markup(speech, (mood, intensity))` and sends `{"action": "PLAY_OUTPUT", "output": {"text": speech, "markup": markup}}`.
  - `send_telehealth_interrupt(device_id)` sends `{"action": "INTERRUPT"}`.
  - `send_wakeup_to_bot(device_id)` — ALREADY EXISTS, gated by `robot_data().device_online(device_id)`, publishes `{"command": "wakeup"}` on the `wakeup` command topic, returns bool. This is the wake transport; do not invent a second one.
  - `send_config_to_bot_json` publishes the merged device config on `/devices/{device_id}/config`.
- `site/hive/mqtt/robot_data.py`: `put_puppet_state` / `get_puppet_state` (lines ~201-209) store the telehealth session state (`READY`, etc.) in memory per robot. A speak sent while `puppet_state` is `None` (not yet `READY`) is a known live failure mode from Oct 28, 2026: the first Puppet speak was published but not heard; the retry after `READY` was heard. The new control API must surface `puppet_state` in its status response and must document that speak/gesture/dance-through-telehealth should wait for `READY` when Puppet mode is in use.
- `site/hive/mqtt/volley.py`, `Volley.ingest_action_tags` (lines ~81-99): model/remote-chat text tags are converted to response actions — `<sleep>` -> `sleep`, `<launch:MODULE[:CONTENT]>` -> `launch` with `module_id` (+ optional `content_id`), `<launch_if_confirmed:...>` -> `launch_if_confirmed`, `<exit>` -> exit. This is the ONLY code-verified mechanism for sleep and for module launch. There is no direct MQTT `sleep` or `dance` command in the codebase.
- `site/hive/content/data.py`: `RECOMMENDABLE_MODULES` includes `{'module_id': 'DANCE', 'category': 'MOVEMENT'}` and `{'module_id': 'ANIMALEXERCISE', 'category': 'MOVEMENT'}`. Note in the same file: "These may not work. In tested some were crashing Unity on Moxie" — this warning applies to customisations, and the same caution must be carried to dance: gate it, test it mocked, live-test only with Stefan's explicit go-ahead, one attempt at a time.
- `doc/AssetBundleMasterManifest.csv`: behaviour-tree assets, all `Default=True` unless noted, include `bht_search`, `bht_searching`, `bht_search_still`, `bht_360_look_around`, `bht_sensoryidlefacetracker_anim`, `bht_180_turn_left/right`, `bht_arms_out`, `bht_beckon_user`, and (per `doc/Markup.md`) `Bht_Sleeping_Zero_Pose` ("eyes closed, upright pose"). Markup behaviour-tree tag format is documented in `doc/Markup.md` (`<mark name="cmd:behaviour-tree,data:{...behaviour+:+<Lbl>...}"/>`).
- `site/hive/automarkup/`: `markup.py` + `markup_types/markup_behavior.py` (`MarkupBehavior`) is the server markup engine. Markup is how the robot is told to move/gesture during speech; there is no standalone robot pose/gesture MQTT command in the codebase.
- NO wheel / motor / joystick / drive API exists anywhere in the clone. Verified by the earlier bridge-plan audit and re-checked here: the only movement vocabulary is gestures, dance/exercise modules, and face-search behaviour trees. The new control API MUST NOT expose a drive command, and must not invent wheel topics, protobufs, or motor functions.

## A.2 Muse Spark as an OPTIONAL chat provider (from Stage 1, adopted unchanged)

- GPT stays default at both levels. Global `chat_provider` (`openai` / `muse_spark`, default `openai`) on `HiveConfiguration`; per-conversation override via the existing dormant `SinglePromptChat.vendor` column (`AIVendor.OPEN_AI = 1`, add Muse Spark = 2).
- Resolution (Stage 1 §B.1, exact): effective provider = conversation vendor if it names a provider whose key is configured; else global `chat_provider` if its key is configured; else `openai`. If the RESOLVED provider has no key, FAIL LOUDLY (log ERROR, speak the existing fallback line) — never silently fall back to the other provider, never bill a provider the user did not select.
- Client: `site/hive/mqtt/ai_factory.py` keeps `set_openai_key` / `create_openai()` with identical semantics (no `base_url` for OpenAI). Add `set_muse_spark_key` / `create_muse_spark()` returning `OpenAI(api_key=<key>, base_url="https://api.meta.ai/v1")`, plus a chat-only dispatch helper `create_chat_client(provider)`. Base-URL constant lives in `ai_factory.py` only. Chat timeout ~20 s on both constructors (new; today neither sets a timeout).
- Model: standard `muse-spark-1.3` only as the default Spark choice; contributor variant `muse-spark-1.3-contributor` only as an explicit, non-default, second choice with a plain-language data-use sentence (Stage 1 §B.3). Never a code default; never auto-substituted. GPT code default stays `gpt-6-luna`.
- Request shaping for Spark (Stage 1 §B.4, exact): `max_completion_tokens` (never `max_tokens`), OMIT `temperature` entirely, `reasoning_effort="low"` (single named constant in `conversations.py`), via a new provider-aware `completion_options_for_provider(provider, model, max_tokens, temperature)` that DELEGATES to the existing `completion_options` unchanged for OpenAI. Both call sites must use it: `SingleContextChatSession.next_response` and `summarize`.
- STT isolation (critical): `zmq_stt_handler.py` `STTHandler.get_stt_client` must keep calling `create_openai()` explicitly. Whisper (`whisper-1`) stays OpenAI even when chat is Spark. If only a Spark key is configured, STT fails with its existing `error_code = 66`, never redirects audio to Meta.
- Setup UI: additive only to `setup.html` + `hive_configure` (provider selector, Spark key field with blank-means-keep, Spark model selector, read-only key-presence status line). Never log a key, never render a stored key back into HTML, never send a chat key to the robot.

## A.3 Full Control API — design (server side only, no robot protocol change)

New surface: extend `puppet_api` in `site/hive/views.py` with new POST commands, keeping the existing GET shape and adding `control_enabled` / `dance_enabled` flags to the GET response where relevant. All new commands:
- validate the device exists (else `HttpResponseBadRequest`, same as today),
- validate the command's parameters against an explicit allowlist (below) and reject anything else with a 400, never pass raw user text into a topic, module id, or behaviour-tree label,
- return `{'result': True/False, 'command': <name>, ...}` (never just `{'result': True}` for new commands, so a caller can tell which command was shaped),
- log provider/command/module/behaviour at INFO/WARNING (never speech content beyond what existing logs already record, never keys),
- are shaped-and-published through the existing `MoxieServer` methods only — no new MQTT topics, no new protobufs.

### Explicitly OUT of v1
- Any wheel/motor/drive command, any head-angle / joint-angle command, any camera capture, any face-recognition / identity command, any autonomous wandering, any multi-command script/queue, any command that bypasses the allowlists above.
- One movement/turn rule (from the bridge plan, adopted): a caller may send at most one movement-class command (`gesture`, `dance`, `look`, `sleep`) per API call, and the API must not queue a second one behind it. Interrupt is the only way to stop a current output.
- Safety: all control commands are Stefan-initiated only in the live sense (they require a caller holding the server API); the server must not auto-trigger dance/gesture/look/sleep on a schedule, on wake, or on any chat turn unless Stefan explicitly configures such a trigger in a later stage.

## A.4 TTS phonetic rule (live-confirmed Oct 28, 2026)
- Moxie's TTS mangles the word "Mycroft". In ANY spoken text sent through this control API (speak, and speak+gesture), the name must be rendered as two words, "my croft" — NOT "Mycroft", NOT "my craft" (both were tried live; "my craft" was rejected, "my croft" was confirmed better).
- Implementation: a single pure function, e.g. `phonetic_name(text)` in the control module, that substitutes the name case-insensitively, word-boundaried, and is applied at the API boundary (in `puppet_api` speak handling and in any control path that carries speech), NOT inside the markup engine and NOT inside the chat model path (chat turns keep the user's text as written; only the spoken control surface applies the substitution, so a chat transcript is never silently rewritten).
- Tests must cover: "Mycroft" -> "my croft", "MYCROFT" -> "my croft" (case handling documented in the test), "my craft" left alone (it is already a spoken form, not the name), and a word containing the name as a substring (e.g. "Mycroftian") NOT substituted.

## A.5 Tests required before Stage B is called done (test-list, Stage A)
- Provider resolution: GPT default with no config; global Spark with key; per-conversation vendor override; resolved-provider-with-no-key fails loudly (no silent fallback); vendor value for an unknown provider is rejected.
- Spark request shaping: `max_completion_tokens` used, `temperature` absent, `reasoning_effort == "low"`, base_url `https://api.meta.ai/v1`, timeout ~20 s; OpenAI path returns EXACTLY the existing `completion_options` output (regression gate, existing `test_chat_models.py` must pass unmodified in behaviour).
- STT isolation: STT client construction still calls `create_openai()` and is unaffected by a Spark chat selection (mocked, no network, no key values in tests — use fake placeholder keys only).
- Control command shaping (mocked MQTT client, no broker, no robot): speak (with phonetic substitution), interrupt, enable/disable, gesture (allowlisted tree only; non-allowlisted tree rejected with 400), dance (flag off -> rejected; flag on -> launch payload with `module_id=DANCE` and no other module), look (allowlisted trees only; default tree), wake (online -> wakeup payload; offline -> `result: False`, no publish), sleep (sleep response-action payload, not a pose), status (no publish, correct flags).
- Mocked-MQTT integration: a fake `MoxieServer` client records published topics/payloads for a full sequence (enable -> speak -> gesture -> look -> dance (flag on) -> interrupt -> sleep -> disable) and asserts topic names (`/devices/{id}/commands/telehealth`, `/devices/{id}/commands/wakeup`, `/devices/{id}/commands/remote_chat`) and payload shapes.
- Negative tests: unknown command -> 400; unknown device pk -> 400; gesture with a non-manifest label -> 400; dance with a caller-supplied module id other than DANCE -> 400; speak with intensity outside 0.0-1.0 -> 400; two movement commands in one call -> 400.
- Existing suites must stay green: `site/hive/test_chat_models.py` and `site/hive/test_stt.py` (run locally, mocked, no network). NEVER merge on a red gate: if any suite is red, Stage B stops and the checkpoint records the failure.
